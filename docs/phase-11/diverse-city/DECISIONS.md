| DCFC-D104 | The approved Diverse City visual does not map to `cinematic@1`. It becomes its own new neutral reusable template, registered as `academy@1`, following the same extraction precedent as `clubhouse@1` (Lions). | Christian approved on 2026-07-31. `PLATFORM-GAP-ANALYSIS.md` found `cinematic@1` registers only `cinematic.hero`/`cinematic.gallery` (plus the shared `shared.next-match`/`shared.history`) — missing shop-feature, sponsor-carousel, standings, and programs-pathway sections Diverse City needs regardless of template choice — and no existing font pack matches Diverse City's Montserrat/Inter/DM Sans stack. | DCFC-D105 | General tenant video is an approved capability, built as real self-hosted video (not a YouTube-embed) via a third-party video CDN — Bunny.net Stream — rather than in-house transcoding on Vercel/Supabase. Format/duration/dimension/size/poster/processing rules are not finalized by this decision; those are `DCFC-201`/`DCFC-202` implementation detail. | Christian approved on 2026-07-31 after a cost/build comparison. Rose City's only existing video ("legacy" `club.slug === "rose-city"` branch in `components/Hero.tsx`, a hardcoded Supabase Storage URL) is not a reusable capability, so this is genuinely new platform work either way. In-house transcoding was rejected: Vercel's serverless functions are a poor fit for video encoding (execution-time/memory limits, the same class of problem that previously forced `sharp`/`libvips` out of the media-cleanup runtime), and raw storage bandwidth (Supabase Storage egress $0.09/GB uncached, Vercel Blob $0.05/GB) both cost more per GB than a purpose-built video CDN at any realistic scale. Modeled cost at 10/20/50/100 clubs (2 short clips/club, ~500 monthly visits/club): Bunny.net Stream was cheapest at every scale (~$1.25 at 10 clubs, ~$12.50 at 100 clubs), with free standard H.264 encoding and a flat $1/mo minimum. Known tradeoffs accepted: less infrastructure control and weaker built-in analytics than Mux, and a smaller network than Cloudflare — judged acceptable for simple looping background/story videos with admin swap-in-out, not live streaming or DRM. Christian signed up for a Bunny.net account (with $20 starting credit) separately from this session. |
| DCFC-D108 | Tier gating for the three new domains: **Contact is Starter-accessible**; **Programs is Pro-only**; **Tryouts is Pro-only**. Implemented by adding `'contact'` to the `onzio_private.club_has_feature` Starter allowlist, while `programs` and `tryouts` use new feature strings that are Pro-only by default. | Christian confirmed on 2026-07-31. Raised during the `DCFC-103` re-review after discovering `club_has_feature` hardcodes the Starter allowlist `('branding', 'roster', 'schedule', 'homepage', 'about')` and that `can_read_feature` gates anonymous public reads — so an unexamined feature name would have silently made Starter clubs' contact pages render empty in public. Pro-only for Tryouts matches the already-registered `moduleRegistry.tryouts` → `entitlement: "pro"`. Adding `'contact'` to the allowlist was chosen over reusing the existing Starter-allowed `about` feature: reusing `about` carries no security downside (features are tier gates, not permission scopes) but would leave `ADMIN_TABLE_FEATURES` mapping contact tables to `"about"`, which is misleading to future readers. The allowlist change is purely additive and cannot affect existing tables. See `DOMAIN-DESIGN.md` for the implementation notes and the required `DCFC-201` contract coverage. |
| DCFC-D109 | The normalized domain design in `DOMAIN-DESIGN.md` (`onzio.programs`, `onzio.contact_profile`, `onzio.contact_page_content`, `onzio.tryouts`) is approved as the `DCFC-202` implementation target, including an explicit column-constraint policy. This closes `DCFC-103` and Phase 1. | Christian approved on 2026-07-31 after a verification pass that re-checked the design's load-bearing claims against real migration source rather than the draft's assertions: the `club_has_feature` Starter allowlist, the pre-existing `onzio.site_social_links` table, `media_assets.surface` being regex-constrained free-form rather than an enum, the absence of any existing email/phone column, and the `homepage_hero_content` singleton shape all confirmed. Christian additionally asked that column-length and URL-shape constraints be specified in the design rather than left for `DCFC-202` to decide while writing SQL. The added policy distinguishes `between 1 and N` (required, no default) from `<= N` (`not null default ''`, where empty is a legitimate unset value), and explicitly rejects reusing `homepage_hero_content`'s internal-path-only href regex for `programs.external_cta_href`/`tryouts.registration_href` — that pattern would reject every external registration URL those columns exist to hold. External-capable href columns instead mirror the `''`/local-path/`http:`/`https:`/`mailto:` allowlist already enforced in `lib/admin-data-contract.ts`. Approval does not authorize writing or applying the migration. |
| DCFC-D103 | Tryouts supports multiple structured event rows, not a single-opportunity singleton. Each row gets its own status, date, location, cost, and registration link, similar in shape to `matches`/`players` (a real table with an admin list/create/edit/reorder flow), not a single-form singleton like `homepage_hero_content`. | Christian confirmed on 2026-07-31 that running simultaneous tryout opportunities across the club's four distinct programs (Youth Academy, Special Kickers, Special Olympics, UPSL Men's Teams) — each with different eligibility and plausibly different windows — is a real, near-term scenario, not a hypothetical. Building the singleton model DCFC-002 shipped and later migrating to structured rows would require a real schema migration; building structured rows now avoids that. Per-row association to a specific program (e.g. an optional `program_id` reference) is left as `DCFC-202` schema detail, not decided here. |
| DCFC-D110 | Resolve the `academy@1` / `bebas-inter` font-pack compatibility inconsistency by **adding `"academy@1"` to `fontPacks["bebas-inter"].compatibleTemplates`**, treating `bebas-inter` as the universal fallback pack every template supports — rather than removing `bebas-inter` from `academy@1.compatibleFontPacks`. `DCFC-203` should also add a contract asserting bidirectional font-pack agreement so this class of drift cannot recur. | Christian approved on 2026-08-01. A `DCFC-203` audit found `academy@1.compatibleFontPacks` includes `bebas-inter` while `fontPacks["bebas-inter"].compatibleTemplates` omits `academy@1` — the only such disagreement among the four templates, so it was introduced with `academy@1`. It is reachable, not theoretical: `switchTemplate` keeps the font pack by reading the template's list (`packages/presentation/index.ts:839`) and validation then rejects the document by reading the font pack's list (`packages/presentation/index.ts:701`), so switching a `clubhouse@1` or `heritage@1` club onto `academy@1` emits a document that fails its own validation. The universal-fallback reading matches how `bebas-inter` is already registered for the other three templates. The rejected alternative was defensible — `DCFC-D104` found no existing pack matched Diverse City's Montserrat/Inter/DM Sans stack — but it would have made `academy@1` the only template with no fallback pack. |

## Decision Rules

- Agents may document options and evidence but may not silently resolve an open
  product or architecture decision.
- A decision that changes platform architecture must also update
  `docs/onzio-platform-plan.md` after Christian approves it.
- When a decision is accepted or superseded, record the date, approver, and
  evidence in this file and update affected work packages and `STATUS.md`.
