The older [production deployment `dpl_8wpeJALJegj8XQnWBbBtxnVZwVij`](https://vercel.com/404christianns-projects/onzio-platform/8wpeJALJegj8XQnWBbBtxnVZwVij) from `589f80192b3cfb1b979c239a14976ec769581901` is still `READY`. It predates #77's code-site ownership change, but its source already selected `AcademyBrandedShell` for `academy@1`. It is **not a proven visual fallback**. Its deployment URL redirects unauthenticated requests to Vercel SSO, so its runtime was not inspected. The two newest marked candidates are the current PR #81 deployment and the preceding PR #82 deployment; those commits changed documentation and loop guidance, not the Academy renderer. A rollback to the immediately previous deployment would not restore a different Diverse City design. The older build also predates #55's v1 retirement and the published-presentation/editor binding fix `ad441ee`, so promoting it could reverse shared-project behavior. No migration file differs between `589f801` and current main, but that check does not prove the old deployment's environment or runtime compatibility.

A read-only Supabase migration listing on November 3 found 57 production migration versions matching all 57 checked-in versions, with latest `20261030170000`. This is a point-in-time parity check, not a backup or approval to run a production deployment.

[Vercel rollback](https://vercel.com/docs/cli/rollback) changes production traffic for the project, not one tenant. Vercel reports this project's team plan as Hobby, which limits rollback to the immediately previous production deployment. The older `dpl_8wpeJALJegj8XQnWBbBtxnVZwVij` is sixth in production history and is not eligible for an exact targeted rollback on this plan. [Vercel promote](https://vercel.com/docs/cli/promote) can point production traffic to a named existing deployment, but promotion of this exact target has not been attempted or proven here. Either action would affect Rose City as well as Diverse City because they share the project. No verified, exact Diverse City-only rollback path has been identified.

For a **future single production deployment**, the then-current deployment would become the immediately previous one. Hobby's one-step rollback could return the whole project to that deployment, provided no intervening production deployment changes the history. The release operator must inspect the deployment history immediately before invoking rollback and stop if the recorded starting deployment is no longer the immediate predecessor. This is a documented platform procedure, not an executed rollback proof or a route back to a distinct pre-Academy design.
